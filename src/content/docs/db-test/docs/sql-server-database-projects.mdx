A SQL Server database project (SSDT, or the SDK-style `Microsoft.Build.Sql`) keeps one object per file. The objects depend on each other across folders, in both directions: a table in `dbo/Tables` has a computed column calling a function in `dbo/Functions`, which reads another table in `dbo/Tables`.

No file order applies that, not even `OrderedDirectories`. The project builds into a `.dacpac`, and `DbTest.MsSql.Dacpac` deploys it with DacFx, in dependency order.

{/* not in upstream: illustrative */}

```bash
dotnet add package DbTest.MsSql.Dacpac
```

:::note
`DacpacSchemaSource` deploys to SQL Server only. With any other engine, setup throws a `DbTestException` before a container starts.
:::

## What to know

### A missing dacpac fails before any container starts

The source checks its configuration before the container starts, so a mistake fails in milliseconds instead of after an image pull and a server boot. A missing dacpac throws a `DbTestException` with the full path it looked for:

{/* not in upstream: illustrative */}

```text
Dacpac not found at '<full path>'. Build the .sqlproj and copy its .dacpac next to the tests ...
```

A dacpac that SQL Server rejects is different: it fails setup with a `SchemaApplyException` naming the dacpac and the server's error. The password is removed from the message.

### `SchemaSource` and `SchemaRoot` are exclusive

A schema source carries its own location and options. Setting `SchemaSource` together with `SchemaRoot` or `SchemaLoadOptions` throws an `InvalidOperationException` when the first test initializes, instead of ignoring one of them. Override only `SchemaSource`.

To apply a directory through the source model, use `DirectorySchemaSource`.

### Deploy options

Without options, the source deploys with these defaults:

- nothing is dropped (`DropObjectsNotInSource = false`);
- possible data loss does not block the deploy (`BlockOnPossibleDataLoss = false`);
- no new database is created, because the engine already created it (`CreateNewDatabase = false`);
- database-level settings such as the recovery model and filegroups are skipped (`ScriptDatabaseOptions = false`), because a throwaway container has no use for them and they are the likeliest deploy failure there;
- every command is bounded by the engine's command timeout (`CommandTimeout` and `LongRunningCommandTimeout`).

Options you pass are used exactly as given, and a bare `new DacDeployOptions()` has no timeout at all. Start from the defaults:

:::caution
Do not change the options after creating the source. Its key is computed at construction, and applying changed options throws an `InvalidOperationException` rather than letting two different schemas share a container.

### Telemetry

DacFx sends usage telemetry to Microsoft unless the environment variable `DACFX_TELEMETRY_OPTOUT` is `1`. Set `<DacFxTelemetryEnabled>false</DacFxTelemetryEnabled>` in the `.sqlproj` to switch it off at build time too. db-test's own repository does both.
